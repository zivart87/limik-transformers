# LIMIK — правила роботи з проєктом

Це головний файл правил для всіх агентів. CLAUDE.md лише посилається сюди.
Шляхи нижче відраховуються від кореня репозиторію.

## Пріоритет і межі роботи

- Поточні вказівки користувача мають пріоритет над старими рішеннями в документах.
- Усередині документації: AGENTS.md → тематичні правила → TASKS.md/чернетки → історичні записи.
- Нові рішення одразу записувати у відповідний тематичний файл; тут змінювати лише загальні правила та посилання.
- Історія помилок не є чинною інструкцією. Не завантажувати весь архів у кожну сесію.
- Помічати проблеми проактивно, але не розширювати погоджену задачу стороннім рефакторингом.
- Виконувати погоджену роботу без повторних підтверджень. Кількість файлів сама по собі не є причиною зупинки.
- Нову архітектуру, міграцію, зміну деплою чи руйнівні дії поза погодженим обсягом спочатку обговорити.
- Не змінювати тексти, дані, порядок блоків або дизайн поза задачею без причини та погодження.

## Поточний обсяг

- Працюємо над `modular-ai-data-centers/`, якщо користувач не вказав іншу сторінку.
- Еталони компонентів фіксуємо по одному в процесі роботи над відповідним блоком.
- Не створювати наперед каталог нових еталонів і не оголошувати випадкову реалізацію затвердженою.
- Уніфікацію стилів головної та генерацію nav/footer відкладено. Не запускати їх під виглядом прибирання.
- Статус публікації Modular, noindex, sitemap і пункт меню не змінювати під час правок дизайну.

## Проєкт і джерела

- Статичний HTML + CSS + vanilla JS; GSAP/ScrollTrigger і Lenis через CDN.
- Сайт: https://www.limiktransformers.com
- GitHub: `zivart87/limik-transformers`, робоча гілка `main`; хостинг Vercel.
- `assets/css/limik.css` — спільні токени й стилі більшості сторінок.
- Головна `index.html` має власні inline-стилі й не підключає limik.css. Зміна спільного CSS не змінює її автоматично.
- Nav: `nav.html`, `assets/css/nav.css`, `assets/js/nav-loader.js`, `assets/js/nav.js`; footer: `footer.html`, `assets/js/footer.js`.
- `build.js` — старий одноразовий помічник заміни маркера меню, не надійна повторювана збірка. Не запускати для перевірки.
- У vercel.json немає buildCommand; налаштування збірки в кабінеті Vercel не підтверджені. Не стверджувати, що збірки немає або що вона налаштована.
- Не додавати framework/npm/build-процес без окремо погодженої задачі.

## Порядок виконання

1. Прочитати правила за типом задачі, git status і поточний код. Зберегти сторонні незакомічені зміни.
2. Знайти вже реалізований аналог на сайті. Для заданого користувачем зразка пріоритет має саме він, а не завжди головна.
3. Переглянути разом HTML, CSS, JS і вигляд зразка у браузері, включно з інтерактивними станами.
4. Переиспользувати наявні класи/стилі/поведінку. Якщо потрібне копіювання, переносити весь необхідний патерн, змінюючи контент цільового блока.
5. Не винаходити нові кольори, кнопки, іконки, анімації або відступи. Якщо аналога немає і потрібне нове дизайнерське рішення — уточнити.
6. Перевірити результат відповідно до масштабу зміни; перевірки виконує агент, а не користувач.
7. Коротко повідомити, що змінено, що перевірено, що залишилося неперевіреним; зробити окремий коміт.

## Перевірки й інструменти

- Перевірки після правок дозволені й обов'язкові. Стару заборону скасовано.
- Візуальні зміни: зразок і результат на однаковій ширині, desktop + проміжні 1280/1024px + 390/360px, hover/focus/open за потреби.
- Адаптивність перевіряти не лише за відсутністю загального горизонтального скролу. Для кожної зміненої сітки/картки перевірити, що найширший реальний контент не виходить за власний контейнер при 100%, 125% і 150% zoom або на еквівалентно звужених viewport. `overflow: hidden/clip` не вважається виправленням обрізаного змісту.
- У grid/flex-елементів, які мають стискатися, явно задавати `min-width: 0`; карткам і коміркам — внутрішній padding за дизайн-системою. Довгі нерозривні значення мають отримувати `clamp()`, container query або ранній reflow до того, як торкнуться межі. Звичайний текст переноситься природно; не фіксувати висоту текстового рядка без резерву для переносу.
- Анімовані лічильники та тексти перевіряти після завершення анімації з повним фінальним значенням. Проміжне коротше значення не придатне для перевірки переповнення.
- При повторенні готового блока перевіряти його з контентом цільової сторінки: найдовший заголовок, показник, одиницю виміру і текст кнопки. Копія CSS не гарантує адаптивності для довшого контенту.
- Повна сторінка: пройти від hero до footer, звірити всі блоки; SEO/Lighthouse — за правилами verification.md.
- Документація/перенесення: цілісність файлів, посилання, git diff, відсутність змін у робочому коді сайту.
- Не повторювати ті самі перевірки без нової причини; не запускати повний аудит після дрібної правки.
- Використовувати доступні інструменти браузера, пошуку й аналізу. Не вимагати конкретних команд Claude Code або неіснуючих MCP/скілів.
- Скіл обирати за змістом задачі; прочитати його перед застосуванням. Відсутність необов'язкового скіла не блокує роботу.
- Не заявляти про візуальну перевірку, авторизацію або деплой без фактичного підтвердження.

## Git і публікація

- Коміт після логічно завершеної зміни; додавати конкретні файли, не `git add .`.
- Сторонні зміни не включати в коміт. Якщо переноситься вже змінений файл, зберегти його поточний вміст і відокремити попередні правки від організаційного коміту.
- Push батчем наприкінці погодженої серії, коли публікація дозволена користувачем; не після кожної дрібної правки.
- Vercel публікує після push. Не використовувати `vercel deploy`.
- За неможливості коміту або перевірки повідомити конкретну причину, не приховувати незавершений крок.

## Обмеження, які зберігаються

- Жовтий — кнопки та вже затверджені інтерактивні варіанти; декор — синя система. Деталі й винятки в design-system.md.
- Фото спочатку шукати серед наявних assets; не генерувати AI-фото/іконки без зміни рішення користувачем.
- Не вигадувати характеристики, контакти, сертифікації, відгуки, ціни, адреси чи посилання.
- Не збільшувати точки каруселей і не змінювати матрицю продуктів на сторінках ніш без запиту.
- Не додавати llms.txt без прямого запиту.
- Production-медіа — в assets; чернетки — docs; локальні вихідні матеріали — _archive.
