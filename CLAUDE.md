## Рабочий процесс

### Git: коммитить часто, пушить батчами

**Коммитим** после каждого логического изменения (цвет, отступ, блок):
```bash
git add <файлы>
git commit -m "краткое описание"
```

**Пушим** когда тема/задача исчерпана — один push в конце серии правок:
```bash
git push origin main
```

**Почему:** Vercel webhook имеет rate limit — при частых пушах часть деплоев пропускается. Батчинг решает проблему: один push = один деплой.

Vercel деплоит автоматически после push. Вручную `vercel deploy` не использовать.

### Перед созданием новой страницы:
1. Вызвать скил дизайна: `/frontend-design`
2. Прочитать `assets/css/limik.css` — единственный источник правды по дизайн-системе

### Чек-лист перед тем как считать новую страницу готовой

Ответственный за этот чек-лист — я (Claude): прогонять его самостоятельно при создании или существенной правке любой страницы, не дожидаясь просьбы пользователя (см. мета-правило 2). Пользователь не имеет опыта веб-разработки и не может сам это проверить. Ниже — конкретные формулы и грабли, найденные при полном SEO-аудите 5 страниц ниш (2026-08), чтобы не переделывать всё скопом ещё раз.

**Title и meta description — формула**
```
Title:   [Product Type] for [Industry] — [MVA/kV вес] | LIMIK   (55–60 символов)
Meta:    [Список продуктов] for [применение]. [Диапазон]. [Дифференциатор].   (150–160 символов, не больше)
```
- Title и description — уникальные, не совпадают с другими страницами
- Проверять длину `content` в символах перед сохранением, не на глаз — Google обрезает description на ~155–160
- Образец готовой формулировки: `industries/data-centers/index.html` meta description

**Мета-теги и индексация**
- Есть `canonical`, `og:type/url/title/description/image` (+ og:image ширина/высота/тип), `twitter:card`
- Страница добавлена в `sitemap.xml` (кроме страниц с `noindex`, например `thank-you/`, `privacy-policy/`, `disclaimer/`)
- Нет случайного `meta robots noindex` там, где страница должна индексироваться

**Контент должен существовать в «сыром» HTML — не только после JS.** Проверять при каждом SEO/GEO-аудите страницы, отдельно от чек-листа выше: любой значимый текст (не декоративная анимация) обязан присутствовать в HTML-ответе сервера, а не появляться только после выполнения JS в браузере.

- **Почему это отдельный пункт, а не часть "структурированных данных":** классический Googlebot в целом исполняет JS перед индексацией, но не гарантированно и не мгновенно (render budget/timeout). А многие GEO/AEO-краулеры (ChatGPT, Perplexity и им подобные) JS вообще не исполняют — просто читают HTML-ответ как есть. Для них контент, появляющийся только через JS, не существует.
- **Практическая проверка:** `curl <url> | grep "<ожидаемый видимый текст>"` — если фраза не находится в сыром ответе, но видна в браузере, это красный флаг. Быстрее, чем открывать DevTools.
- **Уже пойманный на практике баг (2026-08-08, через Telegram-бот "LIMIK SEO"):** на главной — нулевые on-scroll счётчики в сыром HTML (значение появлялось только после scroll-анимации). На `transformers/power/index.html` — блок «Why LIMIK» подгружался через `<div id="why-block-placeholder">` + `fetch('/why-block.html')`, поэтому в сыром HTML был пустой `<div>`. Исправлено переводом на статичную разметку прямо в HTML.
- **`company/index.html` использует тот же паттерн `why-block-placeholder` + `why-loader.js`** — та же уязвимость там пока не исправлена, при следующей правке этой страницы — сделать то же самое (инлайн статичного `.why-cols` вместо fetch).
- Анимация (word-reveal через `<span>`, GSAP/scroll-эффекты) — не то же самое: там текст физически присутствует в HTML с самого начала, JS только визуально его открывает. Проблема специфично там, где JS `fetch()`/`innerHTML` **добавляет** контент, которого в HTML не было.

**🔴 КРИТИЧЕСКАЯ находка (2026-08-08) — nav и footer грузятся через fetch() на КАЖДОЙ странице сайта, включая главную.** `assets/js/nav-loader.js` (`fetch('/nav.html')` → `#nav-placeholder`) и `assets/js/footer.js` (`fetch('/footer.html')` → `#site-footer`) — это касается пункта выше про «контент в сыром HTML», но вынесено отдельно из-за масштаба: это не один блок на одной странице, а **вся навигационная структура сайта на всех страницах разом**.

- **Что именно отсутствует в сыром HTML:** все ссылки шапки (Transformers → 4 товарные страницы, Industries → 5 страниц ниш, Company/Careers/Contact) и все ссылки футера (те же + Privacy Policy/Disclaimer). Проверено: `curl` по `transformers/power/index.html` находит ссылку на `/transformers/mobile/` только один раз (из cross-sell блока) — ссылки из футера физически нет в ответе сервера.
- **Почему это серьёзнее, чем локальный баг одного блока:** это единственный источник sitewide-перелинковки на сайте (кроме контекстных ссылок внутри контента). Для GEO-краулеров без JS сайт выглядит как набор изолированных страниц без связей между собой.
- **Решение отложено пользователем 2026-08-08** — пока просто зафиксировано, ничего не меняли. Варианты на будущее (обсуждались, ни один не выбран):
  1. Оставить как есть (Google в итоге рендерит JS, риск в основном для GEO/AI-краулеров, не для классического ranking).
  2. Заинлайнить `nav.html`/`footer.html` статикой на каждой странице — надёжнее для SEO/GEO, но теряется удобство «правим в одном месте — меняется везде» (нужно либо мириться с ручной синхронизацией, либо решать иначе).
  3. Собрать build-скрипт (Node), который перед деплоем инлайнит фрагменты во все страницы — сохраняет единый источник правды в исходниках, но это отход от правила проекта «никакого билда» (нужно обсуждать отдельно, осознанно).
- **Если будет решено делать пилот на одной странице** (как с другими блоками в этом документе) — начинать с `transformers/power/index.html`, тем же способом, что уже сделан для `why-block-placeholder` (см. выше).

**Контраст текста — `.spec-lbl` (общий компонент карточки товара, `limik.css`) использовал `#7090B0` на белой карточке — 3.33:1, провал WCAG AA.** Найдено 2026-08-08 при повторном GEO/SEO-аудите, когда проверил все `color: #......` в файле по одному, а не выборочно. Исправлено на `#4E6F91` (5.24:1). Компонент общий — влияет на карточки товаров на главной, `industries/data-centers` и в cross-sell блоке товарных страниц. **Практическая проверка контраста** (делать так, а не на глаз): взять hex текста и hex фона, посчитать через любой WCAG-контраст-калькулятор или формулу relative luminance — цель ≥4.5:1 для обычного текста, ≥3:1 для крупного/жирного от 18.66px.

**Внутритекстовые ссылки (contextual links) — проверять отдельным пунктом, не только карточки/кнопки/футер.** На `transformers/power/index.html` было 0 ссылок внутри `<p>` при ~1380 словах контента — по практике 2026 года ориентир 2–5 ссылок на 1000 слов контекстных ссылок. Добавлены 2 ссылки в FAQ-ответе о разнице Power/Autotransformer/GSU (естественное место — там эти продукты и так упоминаются по тексту). **Не форсировать** ссылки где для них нет естественного повода — лучше меньше по делу, чем больше искусственно.
- **Стиль ссылок внутри текста (новый паттерн, аналога на сайте не было до этого):** `color: var(--blue); text-decoration: underline; text-underline-offset: 2px;`, hover → `var(--navy-dark)`. Пример: `.pt-faq-a p a` на `transformers/power/index.html`. Использовать этот же паттерн для будущих внутритекстовых ссылок на других страницах вместо изобретения нового.

**Семантическая разметка (HTML5 landmarks).** На `transformers/power/index.html` не было ни `<main>`, ни `<article>` — только голые `<section>`. Добавлен `<main>` (оборачивает всё содержимое между nav-placeholder и футером) — 2026-08-08. При аудите остальных страниц проверять то же самое: `grep -c "<main"` — если 0, добавить.

**Заголовки (h1–h6) — структуру проверять на пропуски уровней**, не только на количество h1. Правило 2026 года: нельзя перескакивать (например, h2 → h4 без h3) — это ломает семантику, на которую опираются LLM при суммаризации. Практическая проверка: `grep -oE "<h[1-6][^>]*>" файл.html` и глазами пройтись по последовательности уровней. На `transformers/power/index.html` проверено — пропусков нет.

**llms.txt — НЕ внедрять без явного запроса.** Проверено (август 2026): это неофициальный, не подтверждённый Google стандарт — представитель Google (Gary Illyes) прямо сказал, что Google его не поддерживает и не планирует. Практическое применение сейчас — как routing-слой для AI coding-агентов (OpenAI, Anthropic, Vercel и т.п. используют его именно так), не как SEO/GEO-инструмент для маркетингового сайта. Не тратить время на этот файл, пока не появится подтверждённая ценность.

**Structured data (JSON-LD) — обязательно для industry-страниц и им подобных**
Три блока `<script type="application/ld+json">` перед `</head>` (образец — любая из 5 страниц `industries/*`):
- **FAQPage** — текст question/answer только дословно из видимого на странице FAQ-блока, не перефразировать. Google это не проверяет автоматически, но рассинхрон = грубая ошибка.
- **BreadcrumbList** — только реально существующие страницы. У сайта нет страницы `/industries/` (обзорной), поэтому breadcrumb двухуровневый `Home → [Страница]`, без промежуточного узла «Industries» — не выдумывать несуществующий URL ради «полноты» разметки.
- **Organization** — name/url/logo/description. **Никогда** не добавлять `address`, `foundingDate` (PII-правило проекта) и **не добавлять `sameAs`**, пока ссылки на LinkedIn/Twitter в футере остаются заглушками (`href="#"`) — фиктивные URL в structured data хуже, чем их отсутствие.
- После прогона Google Rich Results Test не удивляться, если он покажет только BreadcrumbList как «eligible»: Google с августа 2023 показывает FAQ rich snippet только авторитетным gov/health-сайтам. Разметка FAQPage всё равно нужна — её читают AI-поисковики (ChatGPT, Perplexity, Google AI Overview).

**Картинки**
- Только `.webp` для фото (не `.jpg`/`.png`) — конвертировать через `ffmpeg -c:v libwebp -quality 82-90`
- Если фото — сток/сгенерированное в исходном разрешении (может быть 4000–6000px) — обязательно уменьшить до ~1900–1920px по длинной стороне перед заливкой в проект, даже если формат уже `.webp`. Раздутое разрешение — не менее частая проблема, чем неправильный формат.
- У каждого `<img>` — атрибуты `width`/`height` (реальные пиксели файла, не CSS-размер) — не даёт CLS
- Декоративным (`aria-hidden="true"`) — всё равно `alt=""`, не пропускать атрибут

**Формы**
- Рядом с кнопкой submit — обязательная строка со ссылкой на `/privacy-policy/` (нужно для комплаенса Google Ads): `By submitting, you agree to our <a href="/privacy-policy/">Privacy Policy</a>.`

**Контраст текста — конкретные значения, которые уже один раз были неверными**
- `#7090B0` (= `var(--text-2)`) — цвет только для **тёмных** фонов (контраст на navy-dark ≈ 5.2:1). На **светлом** фоне (белый/off-white) он проваливает WCAG AA (≈3.3:1) — использовать `#4E6F91` вместо него для мелкого/приглушённого текста на светлом фоне (лейблы в карточках, submit-note у форм)
- `.eyebrow` на тёмном фоне (`.bg-dark`/`.bg-mid`) — обычный `--blue` даёт только 3.2:1, не проходит AA. Правило уже реализовано глобально в `limik.css` (`.bg-dark .eyebrow, .bg-mid .eyebrow { color: var(--blue-lt); }`) — для нового eyebrow на тёмном фоне ничего дополнительно делать не нужно
- Перед тем как менять цвет из-за контраста — **сначала проверить реальный фон элемента** (иногда фон меняется у вложенного контейнера, а не у секции целиком — так один раз перепутал navy-dark с off-white и сделал только хуже)

**HTML-гигиена**
- Ровно один `<h1>` на страницу
- Нет внутренних ссылок на несуществующие страницы/страницы-заглушки
- Нет задвоенных `id`

**Дизайн-система** (объединяет уже существующие правила — см. соответствующие разделы ниже)
- Шрифты по типографической шкале (см. «Чеклист аудита шрифтов»)
- Без точки в конце заголовков h1–h4
- Title Case для h2 (кроме заголовков-цитат — см. исключение)
- Мобильная версия проверена на 390px/360px (padding-top под nav, переносы `<br>` и т.д.)

**Не трогать без явного запроса пользователя**
- Точки-пагинацию каруселей (`.products-dot` и подобные) не увеличивать ради touch-target accessibility — пользователь явно отклонил такую правку, приоритет визуала выше WCAG-техники в этом конкретном месте
- Матрица «продукт × ниша» (какие из 4 продуктов показывать на какой странице индустрии) — решение принято: показывать **все 4 продукта одинаково на всех страницах ниш**, не фильтровать по уместности. Черновой план `limik-data-centers-seo-ppc-plan.md` §6.4 предполагал обратное — это уже неактуально, ориентироваться на текущее решение, не на план

## Cross-sell блок «Other Transformers We Build» (товарные страницы)

Добавлен 2026-08-08 на `transformers/power/index.html` — блок с карточками остальных продуктов сайта, вставляется между последним контентным блоком страницы и футером. При добавлении такого же блока на `transformers/autotransformers/`, `transformers/gsu/`, `transformers/mobile/` — переиспользовать паттерн один в один, меняя только состав карточек (везде показываются все продукты **кроме** того, на чьей странице находимся).

- **Стиль — тёмная секция**, полная копия дизайна карусели «The Transformers Powering the Grid» на главной: `<section class="section bg-dark">` + водяной знак `logo-product.svg` (абс. позиционирование bottom-right, `opacity:0.6`) + заголовок `h2` слева/CTA `.btn.btn-gold` справа в одну строку (на мобайле ≤900px — заголовок и кнопка друг под другом, затем кнопка дублируется под карточками, а в шапке скрывается).
- **Карточки — переиспользуемый компонент `.product-card`** (описан в `limik.css`, общий для главной и товарных страниц): `.product-card-name` / `.product-card-image` (фикс. высота 260px, `object-fit: contain`) / `.product-card-specs` (`.spec-row`/`.spec-lbl`/`.spec-val`) / `.product-link` с золотой icon-link стрелкой (см. паттерн кнопок).
- **Десктоп (>900px) — статичная CSS-сетка**, без точек/стрелок листания: `grid-template-columns: repeat(3, 1fr)`. Карточек всего 3, все видны сразу — карусель не нужна.

## Навигация — обязательные правила для новых страниц

### Отступ от фиксированного nav
Nav — `position: fixed`, поэтому **любой контент на странице должен иметь `padding-top` не меньше высоты nav**:
- Nav с синей полосой (начало страницы): ~128px (`nav-top-strip` ~36px + `nav-inner` ~92px)
- Минимальный безопасный `padding-top` для нехеро-страниц: **160px** (128px + дыхание)
- Для hero-секций: padding задаётся индивидуально (обычно 180–220px)
- На мобайле: 140px достаточно

**Запрещено:** создавать страницу без `padding-top` на первом блоке контента. Контент НЕ ДОЛЖЕН быть обрезан фиксированным nav.

### Скрытие синей полосы при скролле
`nav.js` скрывает `.nav-top-strip` через класс `nav--strip-hidden` только при наличии `data-hero` на `<body>`. На страницах **без hero** полоса тоже должна скрываться — это уже реализовано в `nav.js` (else-ветка). **Не нужно** добавлять `data-hero` на нехеро-страницы.

Остальной сайт использует стандартный `clamp(20px, 2.5vw, 32px)`.

**Мобайл (max-width: 768px) — фиксированные размеры:**
- `h1` hero: **46px**
- `h2`: **36px**

Причина: слово «Transformers» (общее для всех страниц ниш — заголовок вида «Power Transformers for X») само по себе шире 342px (доступная ширина на экране 390px за вычетом паддингов 24+24) при 46px — при таком размере слово обрезается краем экрана (`overflow-x: clip` на `html, body` прячет переполнение вместо переноса). 46px на главной работает только потому, что там нет слова шире ~334px. **Запрещено:** ставить точку в конце заголовков (`h1`–`h4`). Ни в каком блоке, ни на какой странице.

### Title Case для h2

Все слова заголовка `h2` — с заглавной буквы, кроме коротких служебных слов: артикли (`a`, `an`, `the`), короткие союзы (`and`, `but`, `or`, `nor`) и короткие предлоги (`of`, `in`, `on`, `at`, `to`, `by`, `up`, `off`, `out`, `for`, `with`, `from`). **Первое и последнее слово заголовка — всегда с заглавной**, даже если это предлог/артикль (например, «Who It's **For**»).

Пример: «The Future of Data Centers Explained» — не «The future of data centers explained».

Если предлог используется как часть фразового глагола (например, «What We Stand **For**», где «stand for» = «отстаивать»), он не заглушается правилом — остаётся с заглавной, как и остальные полнозначные слова.

**Исключение — заголовки-цитаты в узких карточках** (`.dcq-left-title` на страницах `industries/*`, `.caf-left-title` на `careers/`, `.rq-left-title` на `request-quote/`): оформлены как обычное предложение с маленькой буквы (кроме первого слова) — осознанный дизайн-паттерн для подписи/цитаты поверх фото, Title Case на них не распространяется.

### Сетка и выравнивание — единые правила для всего сайта

#### Контейнер (основа)
```css
.container { max-width: 1360px; margin: 0 auto; padding: 0 40px; }
@media (max-width: 768px) { .container { padding: 0 24px; } }
```
**Правило:** весь контент внутри `.container`. Горизонтальный отступ — 40px от края контейнера.

#### Горизонтальные отступы по типу секции
| Тип секции | Горизонтальный padding | Пример |
|---|---|---|
| Контент внутри `.container` | 0 (контейнер сам даёт 40px) | `.section .container` |
| Hero / полноширинная без контейнера | **60px** | `.hero-content`, `.co-hero-content` |
| Мобильные hero | 24px | `@media (max-width: 768px)` |
| Карточки и ячейки внутри сетки | **28px** | `.product-card-name`, `.product-card-specs` |

**Критично:** если секция не использует `.container` — горизонтальный padding строго **60px** (десктоп) и **24px** (мобайл). Никаких `72px`, `80px` и других произвольных значений — это ломает выравнивание относительно других страниц.

#### Двухколоночные секции (фото | текст)

**Главное правило сайта:** левая граница контейнера — жёсткая. Ни фото, ни фон, ни текст не выходят левее `.container`. Справа — фото/фон могут уходить до края экрана.

**Правильный паттерн для split-секций:**
```html
<section class="story-section">       <!-- фон секции может быть любым -->
  <div class="container">             <!-- контент строго внутри контейнера -->
    <div class="story-grid">          <!-- display: grid; grid-template-columns: 1fr 1fr -->
      <div class="story-img">...</div>    <!-- фото слева, bounded контейнером -->
      <div class="story-text">...</div>   <!-- текст справа, bounded контейнером -->
    </div>
  </div>
</section>
```
```css
.story-grid { display: grid; grid-template-columns: 1fr 1fr; min-height: 600px; }
.story-img  { position: relative; overflow: hidden; }
.story-img img { position: absolute; inset: 0; width: 100%; height: 100%; object-fit: cover; }
.story-text { padding: 80px 40px 80px 60px; }  /* 40px = container padding, 60px от центра */
```

Если фото нужно пустить вправо за край экрана — только абсолютным позиционированием с `calc((100vw - 1360px) / 2)`, как в `about-overlay-photo` на главной.

#### Вертикальные отступы секций
- `.section` — `padding: 120px 0`
- `.section-lg` — `padding: 160px 0`
- `.section-sm` — `padding: 64px 0`

На мобайле `.section`/`.section-lg`/`.section-sm` из `limik.css` уменьшаются автоматически (≤991px → 80px, ≤768px → 60px). **Если секция описана кастомным классом с собственным `padding` (не через `.section`)** — мобильное уменьшение нужно прописывать вручную, иначе останется десктопный отступ (120px) и появится лишний воздух. Стандартное мобильное значение для такого кастомного `padding: 120px 0` — **`80px 0`** в медиа-запросе `≤900px`. Проверять при любом аудите: `grep -n "padding: 120px"` по файлу и сверять, что у каждого совпадения есть мобильный override.

**Две секции подряд с одинаковым цветом фона — одинарный отступ, не двойной.** Если у соседних секций фон совпадает (например, обе `--white` или обе `--off-white`), сумма `padding-bottom` первой + `padding-top` второй (120+120=240px) визуально сливается в один неоправданно большой разрыв — границы между блоками не видно, поэтому взгляд считывает это как избыточный воздух. Решение: обнулить верхний паддинг второй секции (`padding-top: 0`), оставив только одну секцию отступа между ними. Не компенсировать это добавлением фона другого цвета — фон меняют только если это осмысленно для дизайна, а не как способ замаскировать двойной отступ. Пример: `.dc-context-section--stack { padding-top: 0; }` на второй из двух идущих подряд `dc-context-section` на `industries/data-centers/`.

### Надзаголовки (eyebrow/label над заголовком секции)
Единый стандарт для всего сайта:
```css
font-size: 13px; font-weight: 800; letter-spacing: 0.07em;
text-transform: uppercase; color: var(--blue); margin-bottom: 32px;
```
Образец: `.founder-eyebrow` на главной (секция "From the Founder"). Единый стандарт для всех секций.
- Цвет всегда синий (акцент). На светлом фоне — `--blue` (#206CB9). **На тёмном фоне (`.bg-dark`/`.bg-mid`) — `--blue-lt` (#4A8FD4), не `--blue`**: обычный `--blue` на `--navy-dark` даёт контраст 3.2:1, ниже минимума WCAG AA (4.5:1); `--blue-lt` даёт 5.1:1. Правило реализовано глобально в limik.css (`.bg-dark .eyebrow, .bg-mid .eyebrow { color: var(--blue-lt); }`) — для нового eyebrow на тёмном фоне ничего дополнительно делать не нужно, просто использовать класс `.eyebrow` как обычно.
- Не использовать `--text-2`, `--gold` или другие цвета для eyebrow без явного запроса.
- `margin-bottom: 20px` — стандартный отступ до заголовка.

**Критически важно — тег eyebrow:**
- Eyebrow/label **всегда на `<div>`**, никогда на `<p>`.
- `<p>` попадает под общие правила типа `.section p { color: ... }` и теряет нужный цвет.
- `<div class="eyebrow">` изолирован от этих конфликтов.

**Критически важно — селекторы для параграфов:**
- Запрещено писать `.container p { }` или `.card p { }` — это захватывает eyebrow и другие не-параграфные элементы.
- Параграфам давать явный класс: `<p class="section-body">` и стилизовать `.section-body { }`.

### Иконки — два стандартных размера

| Размер | Применение | Образец |
|---|---|---|
| **64×64px** | Крупные иконки в контентных блоках (feature-секции, карточки) | `.why-col-icon` — блок "25 Years / Made in USA / 48 Weeks" |
| **28×28px** | Малые иконки в компактных блоках (табы, списки, мета-данные) | `.industry-tab-icon` — табы Industries на главной |

Цвет иконок всегда `var(--blue)`. Никаких других размеров без явного согласования.

**Стиль иконок — solid-fill, без обводки.** Иконки на сайте — простые, залитые одним цветом (`fill="currentColor"`, viewBox `0 0 24 24`), без `stroke`, без рамок/кругов вокруг них (кроме случаев, когда квадрат-контейнер — часть паттерна icon-link, см. кнопки). Источник — Heroicons (solid, MIT-лицензия, `raw.githubusercontent.com/tailwindlabs/heroicons/master/optimized/24/solid/{name}.svg`), либо уже использованные на сайте flaticon-иконки (`.pt-app-icon` на `transformers/power/`). Не рисовать новые line/stroke-иконки (как было в `.dc-specify-icon` и `.dc-mission-card` изначально) — это устаревший паттерн, заменённый на solid во всех блоках. Перед добавлением новой иконки — подобрать подходящую по смыслу solid-иконку из Heroicons, а не изобретать произвольную.

**Если в Heroicons нет подходящей по смыслу иконки** — искать готовую на Flaticon (есть доступ через подключённый MCP). Выбирать вариант в том же стиле: solid-заливка одним цветом, острые углы, без обводки — под остальные правила этого раздела всё равно нужно подгонять (`fill="currentColor"`, цвет `var(--blue)`, нужный размер 64×64 или 28×28). **Запрещено генерировать иконку через AI** (Magnific и т.п.) — только подбор готовой из существующих библиотек (Heroicons, Flaticon).

**Форма — острые углы, минимум скруглений.** При выборе иконки из библиотеки предпочитать варианты с прямыми, острыми углами (как `bolt`, `squares-2x2`, `chart-bar`). Скруглённые/сильно "мягкие" формы (закруглённые концы линий, сильно скруглённые углы прямоугольников) не в нашем стиле. Если у выбранной иконки скругления неизбежны (например, естественная форма самого объекта) — оставлять минимальные, не смягчать форму специально.

**Сложность — максимально простой силуэт, не иллюстрация.** Это отдельное от "solid vs stroke" требование, и именно на нём уже была допущена грубая ошибка (2026-08-08): при подборе иконок через Magnific/Flaticon для блока "Where LIMIK ... Are Specified" на `autotransformers`/`gsu`/`mobile` были выбраны технически solid (заливка, без обводки) иконки, но при этом перегруженные деталями — вышка с десятками мелких растяжек, трансформатор с мелкой штриховкой-«кирпичом», кран с частой решётчатой структурой, электростанция с прорисованными кирпичами/трубами/лентами. На реальном размере (28–64px) это выглядит грязным пятном, а не читаемым пиктограммом — визуально чужеродно на фоне простых и лаконичных иконок сайта.

- Ориентир сложности — простой грузовик, ромб или звезда: 1 (максимум 2–3) сплошная фигура, без внутренней штриховки, без мелких повторяющихся элементов (кирпичи, решётки, заклёпки, множество тонких перемычек).
- Практическая проверка перед тем как вставить иконку в код: открыть её увеличенной (у Flaticon есть превью) и мысленно сосчитать различимые отдельные детали — если их больше 5–7, иконка не подходит, искать проще.
- Индустриальный смысл (трансформатор, вышка, кран, электростанция) не оправдывает сложную форму — упрощать до силуэта (тело + 1–2 характерных элемента), а не пытаться нарисовать техническую деталировку объекта.
- При сомнении между "более узнаваемая, но сложная" и "более простая, но абстрактная" иконкой — выбирать простую. Лучше менее буквальная ассоциация, чем визуальный шум в ряду карточек.

**Один и тот же смысл — одна и та же иконка на всех страницах.** До 2026-08-08 карточки "Defense"/"Disaster Response & Defense" на `transformers/power/`, `transformers/autotransformers/`, `transformers/mobile/` использовали три разных по рисунку щита — несогласованность заметна при сравнении страниц. Утверждён единый щит с галочкой (Flaticon icon id `1489591`, автор berkahicon, `viewBox 0 0 32 32`) — используется на всех трёх страницах в карточках блока "Where LIMIK ... Are Specified" для любой темы, связанной с defense/security/compliance:

## Правила вёрстки

### Цвет и насыщенность текста — единый стандарт

| Фон | Заголовки | Параграфы | font-weight параграфов |
|---|---|---|---|
| Тёмный (`--navy-dark`, `--navy-mid`) | `var(--white)` | `rgba(255,255,255,0.72)` | 400 |
| Светлый (`--white`, `--off-white`) | `var(--navy-dark)` | `#3A5570` | 400 |

**Стандарт параграфа — применяется ко ВСЕМ `<p>` на любой странице без исключений:**
```css
font-size: 16px; font-weight: 400; line-height: 1.75;
```
При написании CSS для нового компонента — **обязательно** сверить каждый `p { ... }` с этим стандартом перед сохранением. Запрещено писать `14px`, `15px`, `1.6`, `1.65` для контентных параграфов.

**Запрещено:** использовать `var(--text-1)` (`#C4D4E8`) для параграфов — это голубоватый цвет, визуально отличается от стандарта. `--text-1` и `--text-2` используются только для вспомогательных мелких элементов (подписи, мета-текст, футер).

**Запрещено:** `font-weight: 300` для параграфов контента — только `400`.

### Вертикальные отступы между текстовыми блоками

- **Между соседними абзацами (`<p>` + `<p>`)** — `margin-bottom: 20px`.
- **От последнего абзаца до кнопки/CTA, идущей следом** — `margin-bottom: 40px` (больше, чем между абзацами — кнопка визуально отделяется от текста). Реализуется через `p:last-of-type { margin-bottom: 40px; }`, а не увеличением отступа у всех параграфов сразу.

Образец: `.co-intro-inner p` на `careers/index.html`.

### Текст на тёмном фоне
`body` имеет `color: var(--navy-dark)`. Если фон задаётся через `::before` или CSS без класса `bg-dark`/`bg-mid` — **обязательно** задавать цвет текста явно:
```css
color: var(--white);           /* для заголовков и основного текста */
color: rgba(255,255,255,0.72); /* для параграфов */
```
Никогда не полагаться на наследование, если bg-класс отсутствует.

### Частичный тёмный фон (паттерн ::before)
Для секций где тёмный фон покрывает только часть ширины:
```css
.section::before {
  content: ''; position: absolute; inset: 0;
  right: 38%; /* покрывает левые 62% */
  background: var(--navy-dark); z-index: 0;
}
.section .container { position: relative; z-index: 1; }
```

**Критическое правило:** если фон блока отступает от края экрана (не full-bleed — например `left: 24px` на мобайле), контент внутри ОБЯЗАН получить дополнительный внутренний паддинг, чтобы текст не упирался в границу фона. Паддинга `.container` (24px/40px) для этого недостаточно — он выравнивает текст ровно по краю фона (когда оба отсчитываются от одной и той же точки экрана), а не создаёт отступ от него. Добавлять паддинг внутреннему блоку с текстом (не `.container`), стандартное значение — **28px** (см. «Карточки и ячейки внутри сетки»). Проверять на глаз после любого изменения ширины/позиции фонового `::before` или `.photo-block`.

### Фото с нахлестом
```css
.photo-block {
  position: absolute;
  bottom: -320px; /* нахлест вниз */
  height: 560px;
}
/* margin-bottom родителя ВСЕГДА = значению bottom фото */
.parent { margin-bottom: 320px; }
```

### Мобильный блок: текст на цветном фоне + фото внахлёст (паттерн `co-intro` / `about-overlay`)
Повторяющийся блок на мобайле: текстовая карточка на цветном (обычно `--navy-dark`) фоне, под ней — фото, которое нахлёстом заходит вверх на фон. Образец — главная (`.about-overlay-card` + `.about-overlay-photo`), применено на `company/index.html` (`.co-intro-inner` + `.co-intro-photo`).

Фиксированные значения на мобайле:
- **Горизонтальный отступ текста от края фона: `28px`** (см. «Карточки и ячейки внутри сетки») — паддинг вешать на текстовый блок, не на `.container`.
- **Высота фото: `380px`** — единый стандарт для всех мобильных фото в таких блоках.
- **Нахлёст фото на фон: `margin-top: -72px`**.
- **`padding-bottom` текстового блока: `112px`** — резервирует место под нахлёст фото. Видимая синяя полоса между текстом и фото = `112 − 72 = 40px`.
- **Левый край фото = левый край текста** — `margin-left` фото считается так же, как паддинг текста (отступ фона + `28px`), чтобы оба элемента стояли на одной вертикальной линии.

```css
.text-block { padding: 48px 28px 112px; }
.photo-block {
  width: calc(100% - <2×отступ>px);
  height: 380px;
  margin: -72px 0 0 <отступ>px; /* отступ = инсет фона + 28px */
}
```

Ширину и правый отступ фото (flush к краю экрана или с отступом) решать по месту — см. конкретный блок.

### Параллакс (GSAP)
Паттерн для фото-блоков — подключать Lenis + GSAP + ScrollTrigger:
```html
<script src="https://unpkg.com/lenis@1.3.4/dist/lenis.min.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/gsap.min.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/ScrollTrigger.min.js"></script>
```
```javascript
gsap.registerPlugin(ScrollTrigger);
const lenis = new Lenis();
lenis.on('scroll', ScrollTrigger.update);
gsap.ticker.add((time) => { lenis.raf(time * 1000); });
gsap.ticker.lagSmoothing(0);

gsap.fromTo(photoImg,
  { yPercent: -6 },
  { yPercent: 6, ease: 'none',
    scrollTrigger: { trigger: photoEl, start: 'top bottom', end: 'bottom top', scrub: 1.5 }
  }
);
```

## Критически важно: index.html НЕ подключает limik.css

`index.html` (главная страница) содержит ВСЕ свои стили в инлайн `<style>` блоке и **не имеет `<link rel="stylesheet" href="assets/css/limik.css">`**.

Это значит:
- Любые изменения в `limik.css` **не влияют** на главную страницу
- Если нужно изменить стиль на главной — менять нужно в inline `<style>` внутри `index.html`
- Если вносишь в `limik.css` новый nav-паттерн — продублируй его и в `index.html`
- `company/index.html` и другие страницы в подпапках — подключают `limik.css` и НЕ имеют своих nav-стилей

**Обязательная проверка перед правкой CSS в `index.html`:** перед добавлением или изменением любого правила — сначала выполнить поиск по файлу на этот же селектор. В `index.html` ~1100+ строк инлайн-стилей, конфликты специфичности неизбежны если не проверять весь файл целиком. Правило которое добавляется раньше может быть перебито более поздним правилом с той же специфичностью.

## Чеклист аудита шрифтов (выполнять при каждой проверке страницы)

При проверке размеров шрифтов на странице — **не читать CSS блок за блоком**, а сделать grep:
```
grep -n "font-size" файл.html
```
Затем сверить **каждое** найденное значение со стандартом:
- Контентный текст (p, td, li, span с текстом) → `16px / 1.75`
- h1 → `clamp(40px, 6vw, 80px)` (кроме hero с явным обоснованием)
- h2 → `clamp(28px, 4vw, 52px)`
- h3 → `clamp(20px, 2.5vw, 32px)`
- h4 → `16px`
- Eyebrow / label → `13px`
- Мелкие подписи (мета, примечания) → `10px–11px` допустимо

Запрещено: `14px`, `15px`, `1.6`, `1.65` для контентного текста. Таблицы — тот же стандарт что и параграфы.

## Запреты

- **`var(--gold)` — ТОЛЬКО `.btn-gold` и `.nav-cta`**. Иконки, линии, рамки, галочки, стрелки, декоративные элементы — никогда gold. Перед любым `var(--gold)` в новом коде спросить: "это кнопка CTA?" Если нет — заменить на `var(--blue)` или `var(--white)`. При исправлении нарушения gold — **обязательно grep по всему файлу на `var(--gold)` и проверить каждое вхождение**.
- **Не удалять стили из `index.html`** без проверки — там нет fallback на `limik.css`
- **Баги чинятся везде, включая главную.** Правило "не трогать index.html без явной просьбы" отменено (2026-08-08) — если на главной найден баг (устаревший CSS, битая ссылка, неверные данные и т.п.), чинить его наравне с остальными страницами, не дожидаясь отдельного запроса на конкретно эту страницу. Осторожность нужна не потому что правки главной запрещены, а потому что там нет fallback на `limik.css` (см. пункт выше) — перед правкой сверяться с актуальной версией стиля в `limik.css`, если компонент там тоже есть.
- **Не использовать `vercel deploy`** — деплой только через `git push`
- **Не создавать новые CSS-переменные** не добавив их в `limik.css` (и в `:root` в `index.html`)
- **Не размещать медиафайлы в корне** — только в `assets/images/` или `assets/video/`
