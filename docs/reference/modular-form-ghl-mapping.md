# Modular — підключення короткої форми до GHL

Стан: 2026-10-20. Форма `modular-ai-data-centers/v2-draft.html`.
**Відправка вимкнена:** `data-delivery="preview"`. Обробник підготовлено в `assets/js/modular-lead-form.js`; реальну доставку в GHL ще не перевірено. Загальна `/request-quote/` та інші форми не змінені.

## Погоджена форма

- Modular вибрано за замовчуванням; `?product=` може вибрати іншу з шести плиток. Вибір обов’язковий.
- Modular: Target IT capacity + When do you plan to start?; Power / Autotransformer / GSU / Mobile: Transformer rating (MVA) + High-side nominal voltage (kV); Other / Not sure yet: лише термін старту.
- Add project details початково закритий; усе всередині необов’язкове. MVA — неперетинні діапазони, конкретне додатне значення або Not sure yet. Напруга — номінальна напруга високої сторони; Other / Specify voltages відкриває текстове поле для повних вимог, наприклад `HV 115 / LV 13.8` kV. Якщо користувач явно обирає введення власного значення, відповідне поле стає обов’язковим; можна повернутися до Select або Not sure yet й залишити технічні деталі невизначеними. При перемиканні між трансформаторами кожен вибір зберігає свої введені значення локально; приховані поля disabled та виключені із запиту.
- Selected configuration з’являється після Configure з картки; користувач може вибрати Not sure yet, поле залишається видимим. Для іншого продукту воно disabled.
- Full name, Work email, Company обов’язкові; Tell us about your project — необов’язкове. Телефону немає.
- Прев’ю перевіряє поля, не надсилає запит і не стирає введення. Реальна відправка має блокування повторного натискання, очікування до 20 секунд, перевірку HTTP status та повідомлення про непідтверджену доставку при помилці. Автоматичних повторних запитів немає. HTTP 2xx означає прийняття webhook, а не підтверджений запис усіх полів CRM.

Схема наявної інтеграції описана в [ghl-custom-fields.md](ghl-custom-fields.md). Не змінювати глобальні правила workflow без перевірки старих форм.

| `message` | Довільний текст | Наявне поле; перевірити видимість в картці та сповіщенні |
| `mvaSelection` | `lt20`, `20-lt50`, `50-lt100`, `100-lt200`, `200-lt400`, `400plus`, `exact`, `unsure` | **Нове** Text / dropdown: вибір діапазону або способу відповіді; не підміняти ним точне значення MVA |

| `requiredVoltage` | Власні вимоги до напруг у kV, довільний рядок | **Нове** поле Text; лише для `voltageSelection=custom`; не записувати цілий рядок в `hvVoltage` чи `lvVoltage` |
| `itCapacity` | `lt200`, `0.2-1`, `1-10`, `10plus`, `unsure` | **Нове** поле Text / dropdown із цими значеннями |
| `projectStart` | `now`, `lt6`, `6-12`, `research` | **Нове** поле Text / dropdown із цими значеннями |
| `configuration` | `Core 20`, `Core 40`, `Core Campus` | **Нове** поле Text / dropdown; Not sure yet → ключ не передається |
| `formSource` | `Modular Data Center` | Наявне поле; перевірити фільтри та маршрутизацію |
| `formVersion` | `modular-v2` | Новий маркер версії запиту для відокремлення логіки цієї форми |
| `pageUrl` | Адреса сторінки | Наявне поле |
| `utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content` | Поточна рекламна атрибуція, коли доступна | Зберегти наявне зіставлення |
| `gclid`, `fbclid`, `ga_client_id` | Ідентифікатори, коли доступні | Перевірити `gclid` → `google_click_id`; для `fbclid` у старому звіті залишалася непідтверджена правка `facebook_click_id` |
| `first_utm_*`, `first_gclid`, `first_fbclid`, `first_ga_client_id` | Перше джерело за логікою `utm.js` | Не перезаписувати вже відоме перше джерело контакту |

Підписи IT capacity: `lt200` → Under 200 kW; `0.2-1` → 200 kW to <1 MW; `1-10` → 1 to <10 MW; `10plus` → 10 MW or more; `unsure` → Not sure yet.

Підписи projectStart: `now` → Ready now; `lt6` → Within 6 months; `6-12` → 6–12 months; `research` → Just researching.

Порожні необов’язкові ключі не надсилаються. Вилучені зі старої великої форми `phone`, `lastName`, `city`, `state`, `application`, `quantity`, `mvaRange`, `hvVoltage`, `lvVoltage`, `cooling`, `source` не надсилаються порожніми заглушками. Workflow не повинен вимагати їх або стирати значення наявного контакту через відсутні ключі.

Кожну заявку варто фіксувати окремою приміткою / записом із параметрами саме цього запиту. Не формувати сповіщення з усіх історичних полів контакту: після зміни продукту там можуть залишитися характеристики попередньої заявки.

## Завершення підключення

1. Спеціаліст GHL перевіряє нові поля, варіанти продуктів, контакт без телефону, повідомлення команді й відсутні ключі; стара загальна форма продовжує працювати.
2. На контрольній версії з тестовою адресою команди перевірити шість продуктів, заявку без деталей, повторний email, повідомлення та атрибуцію; звірити результати всередині GHL. Не вважати HTTP 2xx доказом правильного зіставлення.
3. Після підтвердження встановити `data-delivery="live"`, кнопку Send project request; змінити вступ, FAQ про відправку й примітку під кнопкою, узгоджено з реальною роботою форми. Стандартна примітка: Response within 48 hours. All information handled under NDA on request. By submitting, you agree to our Privacy Policy.
4. Оновити `?v=` змінених CSS/JS; коміт і погоджений push. Не змінювати noindex, меню, sitemap або статус публікації Modular. Готовність деплою підтверджувати окремо.
5. Після перевірки робочої форми переходити до перенесення на `/request-quote/`.

## Локальна перевірка

- Синтаксис обох змінених JS перевірений через `node --check`.
- 25 сценаріїв обробника із підставним fetch: прев’ю без запиту, обов’язкові поля, email, шість продуктових варіантів і виключення прихованих характеристик, HTTP-помилка, мережевий збій, timeout, повторне натискання, honeypot, необов’язкові порожні поля та помилка доступу до атрибуції. Сценарії не є перевіркою реального DOM чи CRM.
- Окремо перевірено логіку перемикання продуктів, disabled прихованих полів, незалежне збереження MVA/kV для кожного трансформатора, Not sure yet у конфігурації та невідомий / некоректний параметр product.
- Локальний браузерний перегляд і адаптивність не перевірені: середовище заборонило з’єднання з локальним HTTP-сервером. Реальні заявки не надсилалися, налаштування GHL не перевірені, live-режим не ввімкнено.

## Списки без неоднозначних інженерних значень — 2026-10-20

- MVA позначає повну потужність трансформатора; kW/MW у полі Modular — IT-навантаження. Автоматичної конвертації між ними немає.
- Межі MVA: <20; 20 ≤ S <50; 50 ≤ S <100; 100 ≤ S <200; 200 ≤ S <400; S ≥400 MVA. Приклади граничних значень: 20 → другий діапазон; 50 → третій; 62.5 → третій; 100 → четвертий; 400 → останній. Це категорії потреби в заявці, не заявлений асортимент чи гарантовані межі виробництва LIMIK.
- Той самий нейтральний перелік використовується для чотирьох видів трансформаторів; не встановлюємо непідтверджені межі для окремих продуктів. Enter a specific rating дозволяє будь-яке скінченне додатне значення, включно з дробовим. Значення діапазону не конвертується в його середину чи межу.
- Напруга списку означає тільки **high-side nominal voltage**, у тому числі для GSU; не називаємо її primary/input, бо напрям підвищення/пониження залежить від застосування. Інші напруги, кілька обмоток або повний набір вимог можна вказати через Other / Specify voltages. Не створюємо фіктивні універсальні пари HV/LV і не прирівнюємо номінальну напругу до максимальної напруги обладнання.
- Джерела перевірки термінів: [Hitachi Energy — ratings / windings](https://www.hitachienergy.com/content/dam/pg/products-systems-services/products-systems-services-files/power-transformer-abb-energy-efficiency-ecodesign-regulation.pdf.coredownload.pdf), [system intertie transformers](https://www.hitachienergy.com/us/en/products-and-solutions/transformers/power-transformers/system-intertie-transformers/non-autotransformers). Конкретні категорії форми — UX-рішення для первинної заявки, а не таблиця технічних характеристик із цих джерел.
- IT capacity: видимі підписи уточнено до <200 kW; 200 kW ≤ P <1 MW; 1 ≤ P <10 MW; P ≥10 MW. JSON-коди збережені.
- Відправка залишається preview. Нові `mvaSelection`, `voltageSelection`, `highSideKv` додати в перевірку GHL до ввімкнення live; приховані власні значення не передаються при поверненні до списку / Not sure yet.

Кожна відповідь: HTTP 200, `{"status":"Success: test request received"}`. Це підтверджує приймання тестового зразка webhook, але не створення контакту, зіставлення полів, повідомлення команді чи опублікований workflow GHL. Ці результати має підтвердити спеціаліст CRM. Передано явно тестові utm_source/medium/campaign; справжні gclid/fbclid/GA identifiers не підставлялися.

Запити виконані окремо від інтерфейсу форми; реальна відправка кнопкою на сторінці лишається вимкнена (`preview`). У коді live-обробника після успішного HTTP-відгуку подяка показується всередині форми: Thank you. Your project request has been submitted. Кнопка Request sent заблокована від повторної відправки. При помилці / timeout дані залишаються, подяка не показується. Сценарії обробника перевірені з mock fetch; реальний браузерний ланцюжок кнопка → GHL → подяка ще потребує контрольного тесту після підтвердження workflow. Окрема thank-you сторінка для Modular не використовується.

## Вікно подяки та подія відправки — 2026-11-03

За запитом користувача Modular, Get a Quote та Contact використовують спільний `lead-confirmation.js` / `lead-confirmation.css`: нативний modal dialog із хрестиком, Escape та кнопкою Continue browsing. Закриття залишає відвідувача на поточній сторінці, повертає фокус до форми. Подяка відкривається лише після HTTP 2xx; це підтвердження прийняття webhook, а не всіх подальших дій CRM. Preview Modular не відкриває подяку й не надсилає заявку. `?form-test=1` відкриває тестову подяку, без події конверсії.

Саме відкриття чи закриття вікна не є тригером конверсії. Повторний виклик для тієї самої форми не дублює подію. Тестові заявки виключені з цих двох викликів; поведінку наявних сторонніх тегів усередині GTM не перевірено.

**Залишається:** перевірити доступ і конфігурацію GTM, зіставити `limik_lead_success` із GA4 / Google Ads / Meta, прибрати можливе дублювання наявними тригерами та перевірити події в debug-режимах. Google Ads / Meta snippets у thank-you містять закоментовані заглушки — це не доказ відсутності цих тегів усередині GTM. Інші форми сайту поки використовують стару thank-you сторінку; її не видалено. Preview/live, noindex і sitemap не змінені.

## Аудит залежності конверсій від thank-you — 2026-11-03

Прочитано публічний `https://www.googletagmanager.com/gtm.js?id=GTM-5RH77HDC`, resource version 10. Контейнер доступний для читання без кабінету GTM. Це перевірка опублікованої конфігурації на дату аудиту, не підтвердження приймання подій рекламними кабінетами.

- GA4 `G-SMY5YWBYT2`: тег `generate_lead` (tag_id 12) запускається за одночасних умов: pathname містить `thank-you`, event = `gtagApiGet`.
- Meta pixel `4193629684102100`: тег `fbq("track", "Lead")` (tag_id 16) запускається за pathname, що містить `thank-you`, та event = `gtm.js`. Ініціалізація Meta є в цьому самому контейнері.
- Тригерів `limik_lead_success` в опублікованому контейнері немає. Нова подія сама не заміняє ці два теги. Заміна redirect на dialog без перенесення конверсій змінює вимірювання.
- Це вже стосується Contact і Get a Quote, переведених на dialog у цій роботі: новий helper викликає OpenAI `measure/lead_created` і dataLayer `limik_lead_success`, але не запускає наявні GA4 `generate_lead` / Meta `Lead` на їхніх старих умовах. Modular v2 від початку не переходив на thank-you; і там нова подія також не запускає ці два теги.
- OpenAI `measure/lead_created` на старій thank-you відповідає виклику helper. Відправлення/приймання пікселем в цьому аудиті не тестувалось. Google Ads snippets і Meta snippets безпосередньо в HTML thank-you — закоментовані заглушки; Meta реально є всередині GTM. Прямих Google Ads conversion tags у resource цього контейнера не знайдено; імпорт конверсій з GA4 і налаштування рекламного акаунта не перевірені.
- Стара `/modular-ai-data-centers/` використовує інший GTM-N756WCL: публічна version 1 має порожні tags/predicates/rules. Не плутати її з v2-draft. Вона також викликає іншу OpenAI-команду `event/Lead` до redirect.
- У чотирьох transformer-форм і Careers redirect на thank-you виконується також після network error; transformer-форми не перевіряють response.ok. У п'яти industries response.ok перевіряється, помилка не веде на thank-you. Careers містить заглушку webhook і не передає вкладене резюме. Це наявні проблеми, аудит не змінював обробники.

Виконано локальну перевірку predicates/rules на JSON-даних опублікованого контейнера: старі події на thank-you активують відповідні lead-теги; `limik_lead_success` на request-quote чи Modular v2 — ні. Скрипт GTM не виконувався в тесті; нові заявки й конверсії не надсилалися.

Перед масовим переходом на dialog необхідно відновити еквівалентні GA4 / Meta виклики після HTTP-успіху (через налаштування тригерів GTM або явно в коді з перевіреними ID), зберегти OpenAI та виключити дублювання. Поки це не зроблено, рівнозначність відстеження старого й нового варіантів НЕ підтверджена.


Після аудиту, за рішенням користувача 2026-11-03: Contact і Get a Quote повернуті до переходу на `/thank-you/` після HTTP 2xx. Вони більше не використовують helper/dialog і знову проходять через наявні URL-тригери GTM. Помилки доставки не перенаправляють. Спливаюча подяка залишається лише на Modular v2; підтверджених GA4 / Meta lead-конверсій для неї досі немає. Інші форми й thank-you не змінені.


## Підключення конверсій вікна Modular — 2026-11-03

У `lead-confirmation.js` додано прямі виклики після підтвердженого успіху: GA4 `generate_lead` → наявний `G-SMY5YWBYT2`, Meta `trackSingle` / `Lead` → наявний `4193629684102100`. ID звірені з опублікованим GTM version 10. Використовуються Google tag і Meta pixel, які вже завантажує GTM, повторної ініціалізації немає. Google-подія чергується через наявний gtag/dataLayer; Meta очікується до 10 секунд при пізньому завантаженні GTM. Блокувальники можуть перешкодити передачі. Контактні дані не додаються до цих викликів.

Власник цих двох конверсій для modal-форм — цей JS; `limik_lead_success` поки лишається діагностичною подією. Якщо пізніше її зв'яжуть із цими ж конверсіями в GTM, прямі виклики треба прибрати, щоб уникнути дублювання. Один виклик на форму забезпечує наявний WeakSet. `form-test=1` пропускає всі три конверсії (GA4, Meta, OpenAI), звичайне preview також їх не запускає. Contact / Get a Quote та решта форм збережені на старому redirect.

Це підключення коду, а не підтвердження приймання подій кабінетами. Google Ads ID/label у перевіреному контейнері не знайдені; прямий Ads conversion tag не додано. Можливий імпорт з GA4 не перевірений. Реальну заявку з рекламною конверсією під час цієї правки не надсилали.


## Спрощення загальної Get a Quote — 2026-11-03

За погодженим користувачем переліком підготовлено локальну зміну `request-quote/index.html`: три розділи Contact Information (Full Name, Work Email, Company — обов’язкові), Project Requirements (Product Type, додано Modular Data Center / `limik-core`) і Additional Information (попередні Project Description та How did you hear about us). Application, Quantity, усі Technical Parameters, телефон, окреме прізвище, місто й регіон прибрані. SMS-згоди та решту розділу Additional Information не змінено.

Збережено наявний webhook Get a Quote, formSource `Request a Quote Page`, UTM-збирання, GTM/pixels та redirect на `/thank-you/` тільки після HTTP 2xx. Full Name передається як `firstName`; `lastName`, `phone`, `city`, `state`, `application`, `quantity`, `mvaRange`, `hvVoltage`, `lvVoltage`, `cooling` у запиті взагалі відсутні, а не надіслані порожніми. Не гарантує поведінку стороннього workflow GHL: до перевірки не стверджувати, що існуючі поля контакту не очистяться або що маршрут коректно прийме `limik-core` і повне ім’я без телефону. Потрібне окреме підтвердження Надії й контрольна заявка після погодженого розгортання.

Локальна перевірка з підставним fetch без надсилання в CRM: валідація пустої форми, payload Modular (`firstName` повне ім’я, `productType=limik-core`, повідомлення, відсутність прибраних полів), Power (`productType=power`), помилка HTTP не показує успіх. Компонування перевірено на 1340 / 1024 / 360px по межах форми. Реальний webhook, CRM workflow, сповіщення та конверсії не перевірялися.

Уточнення користувача: у Get a Quote плитка Modular Data Center стоїть після Mobile Transformer і перед Not Sure Yet; код `limik-core` не змінено.

Уточнення користувача: поля Full Name, Work Email, Company і список джерела мають висоту 46px; плитки Product Type — мінімальну висоту 46px із запасом на перенос. Project Description не змінено. Стилі цієї сторінки inline, окремий CSS-файл не змінювався.
