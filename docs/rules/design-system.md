# Дизайн: чинні правила

Читати перед візуальними змінами. Шляхи — від кореня репозиторію. AGENTS.md має пріоритет.
Це перенесені специфікації, а не нове затвердження всіх блоків для Modular.

## Дизайн-система (`assets/css/limik.css`)

### Типографическая шкала — глобальная для всего сайта

Определена в `limik.css` (применяется ко всем страницам кроме `index.html`):

| Тег | font-size | font-weight | line-height | letter-spacing |
|---|---|---|---|---|
| `h1` | `clamp(40px, 6vw, 80px)` | 800 | 0.92 | -0.03em |
| `h2` | `clamp(28px, 4vw, 52px)` | 700 | 1.0 | -0.02em |
| `h3` | `clamp(20px, 2.5vw, 32px)` | 700 | 1.1 | -0.01em |
| `h4` | `16px` | 700 | 1.3 | 0 |

**Правило:** не переопределять `font-size` у `h1/h2/h3/h4` без необходимости — использовать глобальный размер из шкалы. Кастомный `font-size` допустим только если компонент требует другой размер (например, hero h1 в инлайн-стилях).

**Исключение — `industries/data-centers/`:** для заголовков внутри контентных карточек/панелей (`.dc-mission-panel h3`, `.dc-specify-card h3`) десктопный максимум `h3` снижен с `32px` до `28px` (`clamp(20px, 2.5vw, 28px)`) — в узких колонках `32px` выглядел слишком крупно относительно текста. Остальной сайт использует стандартный `clamp(20px, 2.5vw, 32px)`.

**Мобайл (max-width: 768px) — фиксированные размеры:**
- `h1` hero: **46px**
- `h2`: **36px**

**Исключение — hero `industries/*` (`.ind-hero h1`):** мобильный размер **36px**, не 46px. Причина: слово «Transformers» (общее для всех страниц ниш — заголовок вида «Power Transformers for X») само по себе шире 342px (доступная ширина на экране 390px за вычетом паддингов 24+24) при 46px — при таком размере слово обрезается краем экрана (`overflow-x: clip` на `html, body` прячет переполнение вместо переноса). 46px на главной работает только потому, что там нет слова шире ~334px. Заодно у `.ind-hero-text` добавлен `min-width: 0` — без него flex-элемент не сжимается до ширины контейнера и растягивает весь блок (включая параграф под заголовком) шире экрана. Проверено на 5 страницах ниш (data-centers, utilities, defense, epc-contractors, renewables) на 390px и 360px. При добавлении новой страницы ниши с этим hero-паттерном — использовать 36px, не 46px.

**Запрещено:** ставить точку в конце заголовков (`h1`–`h4`). Ни в каком блоке, ни на какой странице.

### Title Case для h2

Все слова заголовка `h2` — с заглавной буквы, кроме коротких служебных слов: артикли (`a`, `an`, `the`), короткие союзы (`and`, `but`, `or`, `nor`) и короткие предлоги (`of`, `in`, `on`, `at`, `to`, `by`, `up`, `off`, `out`, `for`, `with`, `from`). **Первое и последнее слово заголовка — всегда с заглавной**, даже если это предлог/артикль (например, «Who It's **For**»).

Пример: «The Future of Data Centers Explained» — не «The future of data centers explained».

Если предлог используется как часть фразового глагола (например, «What We Stand **For**», где «stand for» = «отстаивать»), он не заглушается правилом — остаётся с заглавной, как и остальные полнозначные слова.

**Исключение — заголовки-цитаты в узких карточках** (`.dcq-left-title` на страницах `industries/*`, `.caf-left-title` на `careers/`, `.rq-left-title` на `request-quote/`): оформлены как обычное предложение с маленькой буквы (кроме первого слова) — осознанный дизайн-паттерн для подписи/цитаты поверх фото, Title Case на них не распространяется.

### Цвета — 5 основных цветов сайта

| Переменная | Hex | Применение |
|---|---|---|
| `--navy-dark` | `#09193B` | Основной тёмный фон, основной цвет текста |
| `--gold` | `#FFCF0B` | Кнопки и утверждённые интерактивные варианты; не декор |
| `--blue` | `#206CB9` | Акценты: верхняя полоса nav, иконки, выделение слов в тексте `<em>`, декоративные линии и элементы |
| `--white` | `#FFFFFF` | Светлый фон, текст на тёмном фоне |
| `--off-white` | `#F4F6FA` | Очень светлый синеватый фон секций |

**Критически важные правила по цветам:**
- `--gold` — **для кнопок и утверждённых вариантов** (`.btn-gold`, `.nav-cta`, квадрат icon-link, `.pt-compare-btn`). Никаких gold-текстов, декоративных gold-иконок, gold-`<em>` или gold-линий; фон квадрата icon-link относится к кнопке, не к декору.
- `--blue` — акцент для всего остального: выделение слов (`<em>`), иконки, декоративные линии, бордеры, eyebrow-лейблы.
- Выделять слова цветом в тексте (`<em>` синим) — **только по явному запросу** пользователя. Без запроса — не выделять.
- `--navy-mid` (`#0F2656`) — вспомогательный тёмный фон (используется реже, не входит в 5 основных).

### Сетка и выравнивание — единые правила для всего сайта

#### Контейнер (основа)
```css
.container { max-width: 1360px; margin: 0 auto; padding: 0 40px; }
@media (max-width: 768px) { .container { padding: 0 24px; } }
```
**Правило:** весь контент внутри `.container`. Горизонтальный отступ — 40px от края контейнера.

#### Адаптивність карток і сіток

- Кожна комірка має власний внутрішній padding; `gap` між колонками не замінює відступ контенту від межі комірки.
- Для grid/flex-нащадків, які повинні стискатися, задавати `min-width: 0`.
- Довгі нерозривні показники, одиниці виміру, номери телефонів і CTA перевіряти за найширшим реальним значенням. До переповнення застосувати `clamp()`, container query або змінити кількість колонок на вищому breakpoint.
- `overflow: hidden` або `overflow-x: clip` не використовувати як спосіб приховати обрізаний зміст.
- Після зміни перевіряти desktop, 1280/1024px, 390/360px та reflow при 125%/150% zoom. Окремо звіряти межі дочірнього елемента з його карткою, а не лише `scrollWidth` усієї сторінки.
- Для анімованих лічильників вимірювати межі після завершення анімації, коли в DOM уже показане найдовше фінальне значення.

#### Горизонтальные отступы по типу секции
| Тип секции | Горизонтальный padding | Пример |
|---|---|---|
| Контент внутри `.container` | 0 (контейнер сам даёт 40px) | `.section .container` |
| Hero / полноширинная без контейнера | **60px** | `.hero-content`, `.co-hero-content` |
| Мобильные hero | 24px | `@media (max-width: 768px)` |
| Карточки и ячейки внутри сетки | **28px** | `.product-card-name`, `.product-card-specs` |

**Критично:** если секция не использует `.container` — горизонтальный padding строго **60px** (десктоп) и **24px** (мобайл). Никаких `72px`, `80px` и других произвольных значений — это ломает выравнивание относительно других страниц.

#### Двухколоночные секции (фото | текст)

**Главное правило сайта:** левая граница контейнера — жёсткая. Ни фото, ни фон, ни текст не выходят левее `.container`. Справа — фото/фон могут уходить до края экрана.

**Правильный паттерн для split-секций:**
```html
<section class="story-section">       <!-- фон секции может быть любым -->
  <div class="container">             <!-- контент строго внутри контейнера -->
    <div class="story-grid">          <!-- display: grid; grid-template-columns: 1fr 1fr -->
      <div class="story-img">...</div>    <!-- фото слева, bounded контейнером -->
      <div class="story-text">...</div>   <!-- текст справа, bounded контейнером -->
    </div>
  </div>
</section>
```
```css
.story-grid { display: grid; grid-template-columns: 1fr 1fr; min-height: 600px; }
.story-img  { position: relative; overflow: hidden; }
.story-img img { position: absolute; inset: 0; width: 100%; height: 100%; object-fit: cover; }
.story-text { padding: 80px 40px 80px 60px; }  /* 40px = container padding, 60px от центра */
```

Если фото нужно пустить вправо за край экрана — только абсолютным позиционированием с `calc((100vw - 1360px) / 2)`, как в `about-overlay-photo` на главной.

#### Вертикальные отступы секций
- `.section` — `padding: 120px 0`
- `.section-lg` — `padding: 160px 0`
- `.section-sm` — `padding: 64px 0`

На мобайле `.section`/`.section-lg`/`.section-sm` из `limik.css` уменьшаются автоматически (≤991px → 80px, ≤768px → 60px). **Если секция описана кастомным классом с собственным `padding` (не через `.section`)** — мобильное уменьшение нужно прописывать вручную, иначе останется десктопный отступ (120px) и появится лишний воздух. Стандартное мобильное значение для такого кастомного `padding: 120px 0` — **`80px 0`** в медиа-запросе `≤900px`. Проверять при любом аудите: `grep -n "padding: 120px"` по файлу и сверять, что у каждого совпадения есть мобильный override.

**Две секции подряд с одинаковым цветом фона — одинарный отступ, не двойной.** Если у соседних секций фон совпадает (например, обе `--white` или обе `--off-white`), сумма `padding-bottom` первой + `padding-top` второй (120+120=240px) визуально сливается в один неоправданно большой разрыв — границы между блоками не видно, поэтому взгляд считывает это как избыточный воздух. Решение: обнулить верхний паддинг второй секции (`padding-top: 0`), оставив только одну секцию отступа между ними. Не компенсировать это добавлением фона другого цвета — фон меняют только если это осмысленно для дизайна, а не как способ замаскировать двойной отступ. Пример: `.dc-context-section--stack { padding-top: 0; }` на второй из двух идущих подряд `dc-context-section` на `industries/data-centers/`.

### Надзаголовки (eyebrow/label над заголовком секции)
Базовый стиль `.eyebrow` в limik.css:
```css
font-size: 13px; font-weight: 800; letter-spacing: 0.07em;
text-transform: uppercase; color: var(--blue); margin-bottom: 32px;
```
Образец базового отступа: `.founder-eyebrow` на главной. Отступ компонента может иметь существующий override.
- Цвет всегда синий (акцент). На светлом фоне — `--blue` (#206CB9). **На тёмном фоне (`.bg-dark`/`.bg-mid`) — `--blue-lt` (#4A8FD4), не `--blue`**: обычный `--blue` на `--navy-dark` даёт контраст 3.2:1, ниже минимума WCAG AA (4.5:1); `--blue-lt` даёт 5.1:1. Правило реализовано глобально в limik.css (`.bg-dark .eyebrow, .bg-mid .eyebrow { color: var(--blue-lt); }`) — для нового eyebrow на тёмном фоне ничего дополнительно делать не нужно, просто использовать класс `.eyebrow` как обычно.
- Не использовать `--text-2`, `--gold` или другие цвета для eyebrow без явного запроса.
- База: `margin-bottom: 32px`. В товарном FAQ `.pt-faq-head .eyebrow` — `20px`. Переносити варіант обраного блока; не оголошувати 20px другим глобальним стандартом. Перевіряти фактичний каскад на мобільній ширині.
- Якщо після eyebrow йде двоколонковий header із заголовком та описом, його колонки вирівнювати по верхньому краю (`align-items: start`). `align-items: end/flex-end` візуально збільшує відступ до заголовка залежно від висоти сусіднього опису, навіть коли `margin-bottom` eyebrow формально правильний.

### Адаптивна типографічна група

- Надзаголовок, заголовок, вступний опис і проміжки між ними проєктуються як одна група. Якщо заголовок змінюється через `clamp()`, не залишати eyebrow і lead/intro з фіксованими десктопними розмірами.
- Для нового hero або заголовка секції використовувати обмежений fluid scale: eyebrow — `clamp(10px, ..., 12px)`, вступний опис секції — `clamp(14px, ..., 16px)`, hero lead — `clamp(14px, ..., 17px)`. Значення між мінімумом і максимумом підбирати через `vw`; мінімум захищає читабельність, максимум — десктопну ієрархію.
- Вертикальні проміжки всередині тієї самої групи також робити fluid (`clamp()`), якщо основний заголовок fluid. Для стандартного eyebrow → header діапазон лишається 20–32px; для компактного hero допускається 16–24px.
- Звичайний основний текст сторінки не зменшувати нижче 14px. Eyebrow може мати мінімум 10px, бо це короткий uppercase-лейбл, а не основний зміст.
- Media query використовувати для зміни структури, кількості колонок або окремого мобільного обмеження. Не створювати випадкові фіксовані розміри на проміжних ширинах, якщо пропорцію можна зберегти через `clamp()`.
- Перевіряти типографічну ієрархію не лише на 390/360px, а й при 1024/1280px та browser zoom 125%/150%: eyebrow і lead мають зменшуватися разом із заголовком, без стрибка на breakpoint.

**Критически важно — тег eyebrow:**
- Eyebrow/label **всегда на `<div>`**, никогда на `<p>`.
- `<p>` попадает под общие правила типа `.section p { color: ... }` и теряет нужный цвет.
- `<div class="eyebrow">` изолирован от этих конфликтов.

**Критически важно — селекторы для параграфов:**
- Запрещено писать `.container p { }` или `.card p { }` — это захватывает eyebrow и другие не-параграфные элементы.
- Параграфам давать явный класс: `<p class="section-body">` и стилизовать `.section-body { }`.

### Иконки — два стандартных размера

| Размер | Применение | Образец |
|---|---|---|
| **64×64px** | Крупные иконки в контентных блоках (feature-секции, карточки) | `.why-col-icon` — блок "25 Years / Made in USA / 48 Weeks" |
| **28×28px** | Малые иконки в компактных блоках (табы, списки, мета-данные) | `.industry-tab-icon` — табы Industries на главной |

Цвет иконок всегда `var(--blue)`. Это размеры контентных иконок; служебные стрелки/плюсы/кнопки сохраняют размеры своего существующего компонента.

**Стиль иконок — solid-fill, без обводки.** Иконки на сайте — простые, залитые одним цветом (`fill="currentColor"`, viewBox `0 0 24 24`), без `stroke`, без рамок/кругов вокруг них (кроме случаев, когда квадрат-контейнер — часть паттерна icon-link, см. кнопки). Источник — Heroicons (solid, MIT-лицензия, `raw.githubusercontent.com/tailwindlabs/heroicons/master/optimized/24/solid/{name}.svg`), либо уже использованные на сайте flaticon-иконки (`.pt-app-icon` на `transformers/power/`). Не рисовать новые line/stroke-иконки (как было в `.dc-specify-icon` и `.dc-mission-card` изначально) — это устаревший паттерн, заменённый на solid во всех блоках. Перед добавлением новой иконки — подобрать подходящую по смыслу solid-иконку из Heroicons, а не изобретать произвольную.

**Если в Heroicons нет подходящей по смыслу иконки** — искать готовую на Flaticon (если соответствующий инструмент доступен; не предполагать наличие MCP). Выбирать вариант в том же стиле: solid-заливка одним цветом, острые углы, без обводки — под остальные правила этого раздела всё равно нужно подгонять (`fill="currentColor"`, цвет `var(--blue)`, нужный размер 64×64 или 28×28). **Запрещено генерировать иконку через AI** (Magnific и т.п.) — только подбор готовой из существующих библиотек (Heroicons, Flaticon).

**Форма — острые углы, минимум скруглений.** При выборе иконки из библиотеки предпочитать варианты с прямыми, острыми углами (как `bolt`, `squares-2x2`, `chart-bar`). Скруглённые/сильно "мягкие" формы (закруглённые концы линий, сильно скруглённые углы прямоугольников) не в нашем стиле. Если у выбранной иконки скругления неизбежны (например, естественная форма самого объекта) — оставлять минимальные, не смягчать форму специально.

**Сложность — максимально простой силуэт, не иллюстрация.** Это отдельное от "solid vs stroke" требование, и именно на нём уже была допущена грубая ошибка (2026-08-08): при подборе иконок через Magnific/Flaticon для блока "Where LIMIK ... Are Specified" на `autotransformers`/`gsu`/`mobile` были выбраны технически solid (заливка, без обводки) иконки, но при этом перегруженные деталями — вышка с десятками мелких растяжек, трансформатор с мелкой штриховкой-«кирпичом», кран с частой решётчатой структурой, электростанция с прорисованными кирпичами/трубами/лентами. На реальном размере (28–64px) это выглядит грязным пятном, а не читаемым пиктограммом — визуально чужеродно на фоне простых и лаконичных иконок сайта.

- Ориентир сложности — простой грузовик, ромб или звезда: 1 (максимум 2–3) сплошная фигура, без внутренней штриховки, без мелких повторяющихся элементов (кирпичи, решётки, заклёпки, множество тонких перемычек).
- Практическая проверка перед тем как вставить иконку в код: открыть её увеличенной (у Flaticon есть превью) и мысленно сосчитать различимые отдельные детали — если их больше 5–7, иконка не подходит, искать проще.
- Индустриальный смысл (трансформатор, вышка, кран, электростанция) не оправдывает сложную форму — упрощать до силуэта (тело + 1–2 характерных элемента), а не пытаться нарисовать техническую деталировку объекта.
- При сомнении между "более узнаваемая, но сложная" и "более простая, но абстрактная" иконкой — выбирать простую. Лучше менее буквальная ассоциация, чем визуальный шум в ряду карточек.

**Один и тот же смысл — одна и та же иконка на всех страницах.** До 2026-08-08 карточки "Defense"/"Disaster Response & Defense" на `transformers/power/`, `transformers/autotransformers/`, `transformers/mobile/` использовали три разных по рисунку щита — несогласованность заметна при сравнении страниц. Утверждён единый щит с галочкой (Flaticon icon id `1489591`, автор berkahicon, `viewBox 0 0 32 32`) — используется на всех трёх страницах в карточках блока "Where LIMIK ... Are Specified" для любой темы, связанной с defense/security/compliance:

### Кнопки — два базовых паттерна и существующие исключения

#### 1. Primary CTA — форма заявки (`.btn.btn-gold`)
- Сплошная золотая кнопка
- Используется **только** для перехода на форму заявки ("Get a Quote", "Request a Quote")
- Встречается в nav и в hero-секциях
- `.btn-lg` — увеличенный размер

#### 2. Icon-link — переход на другие страницы
- Визуально: **золотой квадрат** со стрелкой (`--gold` фон, `--navy-dark` стрелка) + текст рядом
- Используется везде кроме формы заявки: "Learn More", "View Industry", "Meet the Full Team" и т.п.
- HTML-паттерн:
```html
<a href="..." class="co-intro-link">
  <span class="co-intro-link-icon">
    <svg width="22" height="16" viewBox="0 -2 22 20" fill="none"><path d="M3 8H19M19 8L12 1M19 8L12 15" stroke="currentColor" stroke-width="2.6" stroke-linecap="round" stroke-linejoin="round"/></svg>
  </span>
  Текст ссылки
</a>
```
- CSS — точные значения (не менять):
```css
.co-intro-link {
  display: inline-flex; align-items: center; gap: 16px;
  font-size: 13px; font-weight: 800; letter-spacing: 0.07em;
  text-transform: uppercase; color: var(--white); /* или --navy-dark на светлом фоне */
}
.co-intro-link-icon {
  display: inline-flex; align-items: center; justify-content: center;
  width: 48px; height: 48px; flex-shrink: 0;
  background: var(--gold); color: var(--navy-dark); border-radius: 2px;
}
.co-intro-link-icon svg { transition: transform 0.1s ease; }
.co-intro-link:hover .co-intro-link-icon svg { transform: rotate(-45deg); }
```
- **Анимация:** стрелка поворачивается на -45° при hover. Не придумывать другую анимацию.

Не добавлять новые outline-кнопки по собственной инициативе. Существующие `.btn-outline-white`/`.btn-outline-dark` не удалять в рамках правки правил: их применение сверять с выбранным пользователем блоком. `.pt-compare-btn` — отдельное ранее утверждённое исключение только для таблицы сравнения.

## Правила вёрстки

### Цвет и насыщенность текста — единый стандарт

| Фон | Заголовки | Параграфы | font-weight параграфов |
|---|---|---|---|
| Тёмный (`--navy-dark`, `--navy-mid`) | `var(--white)` | `rgba(255,255,255,0.72)` | 400 |
| Светлый (`--white`, `--off-white`) | `var(--navy-dark)` | `#3A5570` | 400 |

**Стандарт основного контентного абзаца (не полей, подписей и submit-note; для них см. forms.md):**
```css
font-size: 16px; font-weight: 400; line-height: 1.75;
```
При написании CSS для нового компонента — **обязательно** сверить каждый `p { ... }` с этим стандартом перед сохранением. Запрещено писать `14px`, `15px`, `1.6`, `1.65` для контентных параграфов.

**Запрещено:** использовать `var(--text-1)` (`#C4D4E8`) для параграфов — это голубоватый цвет, визуально отличается от стандарта. `--text-1` и `--text-2` используются только для вспомогательных мелких элементов (подписи, мета-текст, футер).

**Запрещено:** `font-weight: 300` для параграфов контента — только `400`.

### Вертикальные отступы между текстовыми блоками

- **Между соседними абзацами (`<p>` + `<p>`)** — `margin-bottom: 20px`.
- **От последнего абзаца до кнопки/CTA, идущей следом** — `margin-bottom: 40px` (больше, чем между абзацами — кнопка визуально отделяется от текста). Реализуется через `p:last-of-type { margin-bottom: 40px; }`, а не увеличением отступа у всех параграфов сразу.

Образец: `.co-intro-inner p` на `careers/index.html`.

### Текст на тёмном фоне
`body` имеет `color: var(--navy-dark)`. Если фон задаётся через `::before` или CSS без класса `bg-dark`/`bg-mid` — **обязательно** задавать цвет текста явно:
```css
color: var(--white);           /* для заголовков и основного текста */
color: rgba(255,255,255,0.72); /* для параграфов */
```
Никогда не полагаться на наследование, если bg-класс отсутствует.

### Частичный тёмный фон (паттерн ::before)
Для секций где тёмный фон покрывает только часть ширины:
```css
.section::before {
  content: ''; position: absolute; inset: 0;
  right: 38%; /* покрывает левые 62% */
  background: var(--navy-dark); z-index: 0;
}
.section .container { position: relative; z-index: 1; }
```

**Критическое правило:** если фон блока отступает от края экрана (не full-bleed — например `left: 24px` на мобайле), контент внутри ОБЯЗАН получить дополнительный внутренний паддинг, чтобы текст не упирался в границу фона. Паддинга `.container` (24px/40px) для этого недостаточно — он выравнивает текст ровно по краю фона (когда оба отсчитываются от одной и той же точки экрана), а не создаёт отступ от него. Добавлять паддинг внутреннему блоку с текстом (не `.container`), стандартное значение — **28px** (см. «Карточки и ячейки внутри сетки»). Проверять на глаз после любого изменения ширины/позиции фонового `::before` или `.photo-block`.

### Фото с нахлестом
```css
.photo-block {
  position: absolute;
  bottom: -320px; /* нахлест вниз */
  height: 560px;
}
/* margin-bottom родителя ВСЕГДА = значению bottom фото */
.parent { margin-bottom: 320px; }
```

### Мобильный блок: текст на цветном фоне + фото внахлёст (паттерн `co-intro` / `about-overlay`)
Повторяющийся блок на мобайле: текстовая карточка на цветном (обычно `--navy-dark`) фоне, под ней — фото, которое нахлёстом заходит вверх на фон. Образец — главная (`.about-overlay-card` + `.about-overlay-photo`), применено на `company/index.html` (`.co-intro-inner` + `.co-intro-photo`).

Фиксированные значения на мобайле:
- **Горизонтальный отступ текста от края фона: `28px`** (см. «Карточки и ячейки внутри сетки») — паддинг вешать на текстовый блок, не на `.container`.
- **Высота фото: `380px`** — единый стандарт для всех мобильных фото в таких блоках.
- **Нахлёст фото на фон: `margin-top: -72px`**.
- **`padding-bottom` текстового блока: `112px`** — резервирует место под нахлёст фото. Видимая синяя полоса между текстом и фото = `112 − 72 = 40px`.
- **Левый край фото = левый край текста** — `margin-left` фото считается так же, как паддинг текста (отступ фона + `28px`), чтобы оба элемента стояли на одной вертикальной линии.

```css
.text-block { padding: 48px 28px 112px; }
.photo-block {
  width: calc(100% - <2×отступ>px);
  height: 380px;
  margin: -72px 0 0 <отступ>px; /* отступ = инсет фона + 28px */
}
```

Ширину и правый отступ фото (flush к краю экрана или с отступом) решать по месту — см. конкретный блок.

### Параллакс (GSAP)
Паттерн для фото-блоков — подключать Lenis + GSAP + ScrollTrigger:
```html
<script src="https://unpkg.com/lenis@1.3.4/dist/lenis.min.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/gsap.min.js"></script>
<script src="https://cdnjs.cloudflare.com/ajax/libs/gsap/3.12.5/ScrollTrigger.min.js"></script>
```
```javascript
gsap.registerPlugin(ScrollTrigger);
const lenis = new Lenis();
lenis.on('scroll', ScrollTrigger.update);
gsap.ticker.add((time) => { lenis.raf(time * 1000); });
gsap.ticker.lagSmoothing(0);

gsap.fromTo(photoImg,
  { yPercent: -6 },
  { yPercent: 6, ease: 'none',
    scrollTrigger: { trigger: photoEl, start: 'top bottom', end: 'bottom top', scrub: 1.5 }
  }
);
```

### Clip-path утилиты (в limik.css)
```css
.clip-tl { clip-path: polygon(64px 0%, 100% 0%, 100% 100%, 0% 100%, 0% 64px); }
.clip-tr { clip-path: polygon(0% 0%, calc(100% - 64px) 0%, 100% 64px, 100% 100%, 0% 100%); }
```

## Джерела та поточні винятки

Головна має власні inline-стилі; limik.css не підключено. Перед CSS-правкою знайти всі правила відповідного селектора й перевірити каскад. Спільні стилі зараз не уніфікуємо.
Modular: REM; CTA жовті з темно-синім текстом; інші акценти blue/blue-lt; не повертати Manrope/DM Sans чи окрему палітру. Компоненти уточнюються по одному під час роботи.

Hero Modular: три фрази заголовка задані окремими `.mdc-hero-line`. На широких екранах вони мають лишатися трьома рядками: текстовому блоку потрібно до 1080px, а розмір шрифту між 992px і широким desktop плавно підлаштовується під доступну ширину. При зміні CTA, проміжку колонок чи тексту перевіряти переноси на 1100, 1200–1250, 1422 і 2048px; планшетний і мобільний переноси можуть бути іншими.

Підзаголовок Modular: на головній `.hero-sub` має обмеження 500px, що зберігає читабельну довжину рядка. Для довшого тексту Modular `.mdc-hero-lead` використовує адаптивну межу `clamp(500px, 40vw, 640px)`: блок ширшає на desktop, але на вузьких екранах займає доступну ширину батьківського контейнера. Не розтягувати абзац на всю ширину заголовка.

### Оптимізація перед підключенням зображення

- Оригінал зберігати в _archive; у assets підключати оптимізовану копію з описовою назвою. Перевіряти інші використання перед заміною спільного файла.
- Фото: WebP; ширина під реальний розмір блока, для широкого hero орієнтир 1920px по довгій стороні. Не збільшувати малий оригінал. Для вектора/логотипа зберігати SVG; не переводити його у фотоформат.
- Початкова якість WebP 82–90; обирати найменший файл без помітних артефактів на реальному розмірі. Не стискати повторно вже стиснену копію — експортувати з оригіналу. Прибрати зайві метадані, зберегти правильні орієнтацію й кольори.
- Для великих фонів робити менший мобільний варіант, за потреби окреме кадрування. Для img використовувати srcset/sizes або picture; для CSS-фону — media query. Перевірити, що початкове завантаження не тягне обидва варіанти.
- Робочий бюджет, не жорстка межа: hero desktop до 250 КБ, mobile до 120 КБ; перевищення обґрунтувати деталізацією та якістю. Менші контентні фото не повинні автоматично отримувати hero-роздільність.
- Головне зображення першого екрана не lazy-load. Для CSS-фону використовувати preload as=image з точним URL і тим самим media, що в CSS; високий пріоритет лише для критичного зображення. Решта img нижче першого екрана — loading=lazy та decoding=async, якщо це не шкодить їхньому сценарію.
- Для img задавати width/height та змістовний alt; декоративним alt="". CSS-фон не має width/height атрибутів — місце резервує контейнер. Не дублювати декоративний опис у доступності без потреби.
- До завершення перевірити вагу, розміри, HTTP-завантаження та фактичний вигляд на desktop, 390px і 360px: кадрування, читабельність тексту, градієнти, різкість, відсутність зсувів макета. У звіті вказати вагу до/після, не обіцяти виміряного прискорення без вимірювання.
