# SEO та готовність сторінки

Читати для нової сторінки, суттєвої переробки або SEO-аудиту. Шляхи — від кореня репозиторію.
Статуси зі старих аудитів не є підтвердженням поточного стану: перевіряти код.

## Метадані й HTML

- Title унікальний. Для ніші: [Product Type] for [Industry] — [MVA/kV] | LIMIK; для товару: [Product] — [MVA/kV] | LIMIK.
- Орієнтир title 55–60 символів, description 150–160: перевірити довжину, але це редакційна ціль, не гарантія відображення Google.
- Description: продукти, застосування, діапазон і реальна відмінність. Еталон формули — industries/data-centers/index.html.
- canonical; og:type/url/title/description/image та розміри/тип зображення; twitter:card. Синхронізувати тексти.
- sitemap тільки для сторінок, дозволених до індексації. Не знімати навмисний noindex, зокрема з Modular, без рішення про публікацію.
- charset на початку head, перед сторонніми скриптами. Один h1, main, логічна ієрархія заголовків без пропусків, унікальні id.
- Значущий текст існує в початковому HTML. JS-анімація наявного тексту допустима; завантаження тексту через fetch потребує окремої уваги.
- Перевіряти сирий HTML та цільові посилання; DOM після JS не замінює цю перевірку.
- Навігація/footer через fetch — відомий виняток, виправлення відкладене. Не розширювати цю задачу автоматично.
- Why-блок перевіряти на fetch; при погодженій роботі над ним переносити зміст у статичний HTML. company/index.html потребує такої перевірки.
- Контекстні посилання додавати природно, не заради квоти. Орієнтир 2–5 на 1000 слів не жорстка вимога.
- Ссылки в тексті: blue, underline, text-underline-offset:2px; hover navy-dark (патерн .pt-faq-a p a).
- Не вигадувати URL /industries/, соцмережі-заглушки, характеристики чи дані організації.

## Structured data

- FAQPage: питання й відповіді дослівно відповідають видимому FAQ.
- BreadcrumbList: лише реальні сторінки; для ніші Home → поточна сторінка, без неіснуючої /industries/.
- Organization: name/url/logo/description. Без address/foundingDate; sameAs лише після появи реальних затверджених профілів.
- Для 4 товарних сторінок також Product: name, description, image, brand, manufacturer, category, additionalProperty з реальних характеристик.
- Не додавати вигадані offers/review/aggregateRating. JSON має парситися; дані мають збігатися зі сторінкою.
- Наявність розмітки не гарантує rich results. Не обіцяти результатів пошуку на підставі валідного JSON-LD.
- robots.txt перевіряти в межах SEO-задачі; не додавати llms.txt без прямого запиту.

## Контент, медіа й доступність

- Фото WebP, приблизно до 1920px по довгій стороні; width/height відповідають файлу, alt є завжди (декоративним alt="").
- Контраст перевіряти на фактичному фоні: звичайний текст ≥4.5:1, великий ≥3:1.
- #7090B0 не для дрібного тексту на білому; використовувати #4E6F91. Eyebrow на темному — blue-lt.
- Форми: повний submit-note, доступні підписи, коректні помилки й успішний стан; див. forms.md. Реальну заявку без потреби не надсилати.
- Телефон на товарній сторінці біля форми, не лише у fetch-футері; правила .pt-sidebar-call у forms.md.
- Типографіка, заголовки без крапок, Title Case і винятки — design-system.md.

## Повна товарна сторінка

Звірити всю сторінку від hero до footer з відповідним зразком, а не тільки технічні теги:
- Основний опис, застосування, характеристики, форма.
- Why LIMIK у статичному HTML.
- FAQ та контекстні посилання.
- Power Starts Here, універсальний CTA Band.
- Cross-sell і таблиця порівняння з правильною поточною колонкою.
- Nav/footer/back-to-top, мобільна CTA та її взаємодія з footer.
- Всі 4 продукти на сторінках ніш; у cross-sell товарної сторінки — решта 3.
Детальні попередні специфікації — components.md. Не додавати ці секції автоматично до Modular поза погодженим дизайном.
Після завершення значної переробки — перевірки verification.md, включно з mobile Lighthouse.
